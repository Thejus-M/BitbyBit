LangChain, LangGraph, LangSmith: Stop Confusing Them

Three tools, same company, completely different jobs. LangGraph is already running in production at Klarna, Uber, and J.P. Morgan. Most developers still can't explain what it does differently from LangChain.

If you've googled "LangChain vs LangGraph" you already know the confusion. The naming doesn't help: same prefix, same company, similar documentation sites. Most tutorials pick one and ignore the others, so you end up with a half-baked mental model and code that works until it doesn't.

Here's the frame that makes everything click: LangChain builds the pipeline, LangGraph orchestrates the agents, LangSmith watches everything. They are not alternatives. They are layers, and most serious LLM applications end up using all three.

This post explains what each one actually does, where each one breaks down, and how to decide which layer you need for any given problem.

LangChain: The Builder

The problem LangChain was built to solve is vendor lock-in. Before it, switching from OpenAI to Anthropic meant rewriting your API calls, your response parsing, your error handling. LangChain wraps all of that in a standard interface: one .invoke() call works identically across every major model provider.

The core abstraction is LCEL, the LangChain Expression Language. It uses the pipe operator | to connect components the way Unix connects commands. A prompt template, a model, and an output parser chain together like this:

// Python — LCEL chain chain = prompt | llm | output_parser result = chain.invoke({"question": "What is LangGraph?"})

Any component that implements the Runnable interface can sit in that pipe. Swap the model, change the parser, add a retriever in the middle: the rest of the chain stays the same. Beyond the pipe, LangChain ships ready-made components for the most common tasks: document loaders, text splitters, vector store retrievers, conversation memory, structured output parsers.

INPUT User Query
→
COMPONENT Prompt
|
COMPONENT LLM
|
COMPONENT Parser
→
OUTPUT Answer
prompt | llm | parser  ·  .invoke()  ·  .stream()  ·  .batch()
Each component lights up as the input passes through. No state. No branches. One direction. That is LCEL.

The limit of LangChain is exactly that linearity. There is no shared state between invocations, no way to loop back, no branching logic. The input enters, passes through each component in sequence, and exits. For a chatbot, a RAG pipeline, or a document summarizer, that is all you need.

What LCEL gives you for free

Swap .invoke() for .stream() and the chain yields tokens as they arrive. Swap for .batch() and it processes a list of inputs in parallel. The pipe handles all of this with no extra code on your end.

LangGraph: The Director

Real agents don't run in a straight line. A coding agent reads a file, runs a test, sees an error, decides whether to retry or ask the human, retries up to three times, then gives up if it still fails. That control flow has loops, conditionals, and recoverable failures. You cannot express it as an LCEL chain.

LangGraph models agent behavior as a directed graph. Nodes are Python functions that receive the current state and return an update to it. Edges connect nodes. Conditional edges can route to different nodes based on what the state contains. The state itself is a typed dictionary: think of it as a shared backpack that every node reads from and writes to as the execution moves through the graph.

NODE START
NODE AGENT
NODE TOOLS
NODE END
{ state }
⏸ WAITING FOR HUMAN INPUT
needs tool?
done?
State moves through the graph. AGENT calls the LLM; conditional edge checks if a tool is needed. If yes: route to TOOLS, update state, loop back. If no: route to END. The graph pauses when human input is required.

The result is a first-class loop. The agent node calls the model; a conditional edge checks whether the model requested a tool call; the tools node runs the tool and writes the result back into state; the edge routes back to the agent. That cycle repeats until the model decides it has enough information and routes to END instead.

Three features separate LangGraph from a plain LCEL chain: checkpointing (state persists to a database, so long-running agents survive restarts), human-in-the-loop (the graph can pause at any node and wait for a human decision before continuing), and streaming (you can observe every node's input and output as it happens). These are the things production agents actually need.

LangGraph is intentionally low-level

It does not abstract prompts, tools, or memory on your behalf. You wire every node explicitly. That verbosity is the point: complex agent behavior needs visible control flow, not implicit magic. Klarna, Uber, and J.P. Morgan run LangGraph in production exactly because they can see every decision branch.

LangSmith: The Observer

Once your chain or graph is running, you have a new problem: you cannot see inside it. A chain calls a model, the model returns something wrong, and you have no idea which prompt produced the bad output, how long each step took, or how many tokens were consumed. Log files give you strings. You need a trace.

LangSmith is an observability platform that instruments your application. It captures every LLM call, tool invocation, and chain step as a span, then assembles those spans into a trace tree. You see the full execution path, the input and output of every node, the token counts, and the latency, all in one hierarchical view.

→ USER: "summarize this doc"
→ RETRIEVER: fetching chunks
→ LLM: claude-sonnet-4-6
→ PARSER: structured output
▾ rag_chain 890ms
▾ retriever 42ms
▾ llm 820ms
· tokens_in 1,240
· tokens_out 312
Every call in your application becomes a span. LangSmith assembles them into a trace tree showing latency, token counts, and the exact input/output of each node. The retriever took 42ms. The LLM took 820ms. Now you know where to optimize.

LangSmith does not execute your code. It watches it. Your application sends telemetry to LangSmith in the background; adding LANGSMITH_TRACING=true to your environment is enough to start capturing traces if you are using LangChain or LangGraph. For other frameworks, a thin SDK wrapper does the same job.

Beyond tracing, LangSmith handles evaluation at scale. Define a dataset of (input, expected output) pairs, run your chain against all of them, score each output with a custom function or an LLM judge, and track the score over time. Every prompt change gets measured against that baseline before it touches users.

LangSmith is framework-agnostic

You do not need LangChain or LangGraph to use LangSmith. It works with raw Anthropic or OpenAI SDK calls, or any other framework. The tracing SDK is the only dependency. Add it to whatever you are already building.

How They Fit Together

The three tools solve three different problems at three different stages of building. The path from prototype to production almost always follows the same order.

Start with LangChain for the first version. You get a vendor-agnostic model interface, a collection of ready-made components for the most common tasks, and LCEL to wire them into a chain. Most chatbots, RAG pipelines, and Q&A systems never need anything more.

Add LangGraph when the workflow requires state, loops, or branching. LangGraph builds on LangChain components: you can reuse the same models, tools, and retrievers inside a StateGraph node. The upgrade is additive. You are not rewriting the application; you are wrapping the complex parts in a graph.

Add LangSmith before shipping to production. Instrument the application, run your evaluation dataset, establish a quality baseline. Every future change to a prompt or model gets scored against that baseline before it touches users. Without this step, you are guessing whether changes helped or hurt.

Decision Guide

Use this as a starting point, not a rigid rule. Real applications often need multiple patterns at once.

Use LangChain if:

  • Your workflow is linear: user sends input, model processes it, you return output. No state needed between calls.
  • You want provider flexibility: swap OpenAI for Anthropic or Gemini without touching the rest of your code.
  • You are building a chatbot or RAG pipeline: standard components (retrievers, splitters, parsers) cover 90% of the work.

Upgrade to LangGraph if:

  • You need loops or retries: the agent should be able to call a tool, see the result, and decide whether to call another one.
  • You are building a multi-agent system: a coordinator agent that routes tasks to specialist agents requires graph-based orchestration.
  • You need the workflow to pause: a code review agent that waits for human approval before deploying requires human-in-the-loop.
  • You need durable state: the agent runs for hours and must survive restarts without losing its place in the workflow.

Add LangSmith if:

  • You are approaching production: every LLM application that touches real users needs visibility into what the model is actually doing.
  • You need to debug bad outputs: a trace tree shows you the exact prompt, context, and model call that produced any given response.
  • You want to test prompt changes safely: run a new prompt against a dataset of real examples and score the diff before deploying.
The one mistake most teams make

They add LangGraph on day one because agents sound more powerful. Then they spend three weeks debugging control flow that a plain LCEL chain would have handled in an afternoon. Start simple. Move to LangGraph when the linear model breaks, not before.
