If you've ever wondered why running a state-of-the-art LLM seems to need a small server farm, here's the short answer: it's not the math that's slow. It's the memory. Every token your model has "seen" gets stored in something called a KV cache, and that cache grows linearly with context length. Double the context, double the VRAM.

The usual fix has been to just buy more H100s. In early 2026, Google Research published a different approach called TurboQuant: a training-free algorithm that compresses the KV cache to just 3 bits per value, cuts memory by 6×, and speeds up inference by 8× with no accuracy loss.

This post walks through how it actually works, with animations for each step.

The Memory Wall

Think of an LLM like a student taking notes during a very long lecture. Every word the lecturer says, the student writes down two things in their notebook: a Key (a tag to find the word later) and a Value (what the word actually means in context). That notebook is the KV cache.

The problem is simple: the longer the lecture, the bigger the notebook gets. Double the length and you need twice as much desk space. For a 104-billion-parameter model with a 128K context window, that desk space works out to roughly 448 GB of GPU memory. And that's before any actual computation.

As tokens stream in, KV blocks stack up. Compute stays idle at 20% while VRAM fills to 100% and overflows. The GPU is starved, not of math, but of memory.
The uncomfortable truth

A modern H100 GPU has 80 GB of VRAM. The KV cache for one long-context query can easily need 5 or 6 of them. That's why long-context inference costs so much. You're renting entire GPU clusters just to hold notes.

Step 1: PolarQuant. Rotate First, Then Compress

The obvious fix is to use shorter numbers. Replace 16-bit floats with 8-bit or 4-bit. The technical term is quantization.

The problem is that KV cache data is spiky. A few dimensions have huge values (outliers), most are tiny. Uniform quantization either destroys the outliers or wastes precision on the tiny values. Neither is acceptable.

PolarQuant multiplies every vector by a random orthogonal matrix before compressing it. An orthogonal matrix is a rotation: it changes direction but preserves length. A random rotation spreads the "energy" of any vector evenly across all its dimensions. Spikes flatten out. The data becomes smooth and predictable.

R · x
1 · SPIKY CARTESIAN 2 · ROTATED · SMOOTH 3 · SNAPPED TO POLAR RINGS
Messy scatter → random rotation smooths it out → points snap onto polar rings (radius + angle). Compressing angles is cheap; the distribution is now tight and predictable.

After rotation, PolarQuant switches from Cartesian coordinates (x, y, z) to polar coordinates: one radius plus a set of angles. Since the rotation makes all the angles follow a tight, predictable distribution, those angles compress into just a handful of bits without losing meaningful information.

Why this is clever

Normal quantization stores metadata per block: "this block's range is 0–20, that one's 0–500". That overhead adds up. PolarQuant's rotation makes every block behave the same way, so you only store the rule once.

Step 2: QJL. The 1-Bit Correction

PolarQuant handles most of the compression, but the attention mechanism is picky. It computes dot products between Query and Key vectors, and even a small rounding error gets amplified by softmax. Left alone, those errors break the output.

That's where Quantized Johnson-Lindenstrauss (QJL) comes in. Take the leftover rounding error from PolarQuant and represent it with just a single sign bit, either +1 or -1. That bit nudges the dot product back onto the correct value during inference.

A high-precision Query and a compressed Key produce a slightly-off dot product. One sign bit (±1) flies into the math, and the precision gauge snaps to the 16-bit target. No extra bytes, no accuracy loss.

Keys and Values sit in 3 bits, and attention scores come out mathematically indistinguishable from the full 16-bit version. Custom Triton fused attention kernels let the GPU compute dot products directly on compressed data, skipping any decompression step entirely.

74 GB fits on a single H100. Before TurboQuant, the same workload needed five or six H100s just for the cache. The speedup comes from less data moving between VRAM and GPU cores, not from faster arithmetic.

Developer Takeaways

Here's why this matters for anyone building on top of open-source LLMs:

  • Training-free: TurboQuant is "data-oblivious". No retraining, no fine-tuning, no calibration dataset. You apply it to weights you already have.
  • Drop-in for open models: Works with Llama 3, Mistral, Qwen, and other standard transformer architectures out of the box.
  • Local inference gets real: A 128K-context workflow that previously needed a data-center rack now fits on a single high-end card, and eventually on a workstation.
  • Long context becomes cheap: The cost of giving a model a million tokens of history stops being about memory rental and starts being about actual compute.
Bottom line

For years, scaling context windows meant buying more VRAM. TurboQuant shows that a chunk of that cost was covering up an algorithmic gap. The path to accessible, on-device inference runs through math like this, not through bigger GPUs.
